# 基于多 Agent 的电器产品质量检测系统：面试高频问题与参考答案

面向岗位：助理 AI 应用开发工程师  
项目时间：2026.01 -- 2026.04

## 面试口径校准

这份问答按“面试官只能看到简历内容”的前提整理，问题和回答都用自然语言表达，不依赖具体实现细节命名。

- 主线保留：电器质检业务建模、FastAPI 后端业务闭环、多约束排程、CP-SAT 与 SLA 兜底、多 Agent 辅助决策、RAG 知识检索、结构化输出校验、权限审计、评估闭环。
- 主动弱化：数据回放、多策略候选评分。可以说项目早期有过验证和策略比较思路，但简历主线不建议展开为落地成果。
- 安全边界必须讲清楚：大模型只做草稿、解释、推荐、检索问答和通知文案增强，不直接创建订单、不修改排程、不预约设备；所有写操作必须走确定性业务服务、权限校验和人工确认。
- LIMS/ERP 对接建议这样说：项目抽象了可对接 LIMS/ERP 的订单、设备台账、人员班次和认证标准数据模型，封装了业务接口；不要说已经完成真实厂商系统联调。

## 1. 你用一句话介绍这个项目？

参考答案：

这是一个面向电器产品质量检测中心的 AI 应用系统，核心是把订单、检测流程、设备、人员、班次、耗材和 SLA 约束统一建模，生成可执行的检测排程；多 Agent 和大模型主要负责自然语言订单草稿、检测项目推荐、知识检索、排程解释、异常分析和通知文案辅助，最终业务状态仍由后端确定性服务控制。

## 2. 这个项目为什么适合写在 AI 应用开发工程师简历里？

参考答案：

因为它不是简单调用大模型聊天，而是把大模型嵌入真实业务流程。项目里需要解决结构化输出、权限边界、工具调用、业务规则校验、无模型时的兜底、排程算法和评估门禁等问题。岗位要求强调 AI 应用开发和落地工程化，这个项目正好能体现“把 LLM 能力变成可控业务系统”的能力。

## 3. 你在项目中最核心的工作是什么？

参考答案：

我主要做了四类工作：第一，梳理订单、检测项目、设备、人员、认证标准和 SLA 的领域模型；第二，实现订单接入、排程、事件、通知和审计的后端闭环；第三，把排程问题抽象成多资源约束优化，并设计 CP-SAT 求解和 SLA 兜底机制；第四，设计多 Agent 辅助决策链路，让大模型参与解释、草稿提取和推荐，但不直接写业务数据。

## 4. 项目里为什么要用多 Agent，而不是一个大模型提示词解决所有事？

参考答案：

因为每类任务的风险、输入和输出都不一样。订单草稿提取关注字段完整性，项目推荐关注认证标准约束，知识检索关注引用来源，排程解释关注 SLA 和瓶颈，异常分析关注风险等级和处理建议。如果全部塞进一个大提示词，权限和输出边界会很混乱。拆成多 Agent 后，每个 Agent 只做单一职责，方便校验、追踪和兜底。

## 5. 你这个多 Agent 架构属于哪一类？为什么这样设计？

参考答案：

更接近中心化编排架构：先由一个调度/路由角色判断用户意图，再分派给订单、项目识别、知识检索、排程解释、异常分析等专门 Agent。这样做的原因是质检业务不是开放式讨论，而是强约束流程，必须有统一入口和权限控制。参考 Agent 架构设计原则，多 Agent 不一定总比单 Agent 好；只有任务边界清晰、需要分工且要控制风险时，中心化多 Agent 才更合适。

## 6. 如果面试官问 LangGraph 的价值，你怎么回答？

参考答案：

我会从“可控流程”角度回答。传统链式调用更像线性流水线，但多 Agent 业务会有条件分支，比如自然语言请求可能进入订单草稿、知识检索、排程解释或异常分析。LangGraph 这类图式编排更适合把 Agent 看成节点，把路由和状态传递看成边，便于做条件分支、状态共享、轨迹追踪和错误兜底。

## 7. 你如何理解单 Agent 和多 Agent 的取舍？

参考答案：

我不会认为多 Agent 一定更先进。单 Agent 的优势是通信成本低、上下文一致，适合强顺序、工具密集、任务边界不复杂的场景。多 Agent 的优势是分工清晰、可并行、便于做专门校验，但也会带来协调成本和错误传播。这个项目选择多 Agent，是因为订单、知识、排程、异常和通知本身就是不同业务域，需要不同权限和输出约束。

## 8. 自然语言订单录入是怎么做的？

参考答案：

用户可以输入类似“客户送检一批加急电磁兼容样品，希望三天内完成”的描述，系统会抽取订单类型、样品名称、数量、认证类型、期望完成时间和可能涉及的检测项目。抽取结果不会直接创建订单，而是形成订单草稿，并标出不确定字段和置信度，交给人工确认后再进入正式订单创建流程。

## 9. 大模型抽取订单字段出错怎么办？

参考答案：

我做了两层控制。第一层是枚举和类型约束，例如订单优先级只能是普通、加急、VIP，认证类型只能落在系统支持的范围内，数量必须是正数。第二层是人工确认和缺失字段提示，如果模型没有把握或输出不合法，就把字段标为待确认，而不是写入数据库。这样能把模型的不确定性限制在草稿阶段。

## 10. 检测项目推荐如何避免模型乱推荐？

参考答案：

检测项目推荐必须以认证流程为底线。系统会先根据 CCC、CVC 或国际认证生成确定性必检流程，大模型只能在这个业务边界内辅助解释或补充建议。若模型推荐了流程外项目，只能作为可选风险提示，不能自动变成必检项；如果模型漏掉必检项目，系统会按规则补回。这体现了“LLM 辅助判断，规则保底”的原则。

## 11. 项目里的 RAG 解决什么问题？

参考答案：

RAG 主要解决认证标准、设备约束、检测流程说明等知识查询问题。大模型本身不是企业知识库，直接让它回答容易幻觉。RAG 的思路是先从项目知识库检索相关依据，再让模型基于这些依据回答，并附带来源。这样既能减少幻觉，也方便面试官或业务人员追溯答案来自哪里。

## 12. 你怎么理解 RAG 和模型微调的选择？

参考答案：

我会先看问题类型。如果问题是企业内部资料、认证标准、设备约束、流程文档这类外部知识缺失，优先用 RAG，因为知识更新快、需要可追溯，放进知识库比重新训练模型更合适。如果问题是模型长期不能稳定按某种格式输出、领域术语理解差，且有大量高质量标注数据，才考虑微调。这个项目当前更适合 RAG 加规则校验，而不是直接微调。

## 13. 你的 RAG 知识库如何组织？有没有考虑切分问题？

参考答案：

项目里的知识主要是认证流程、设备约束、优先级规则和操作约束，很多内容是结构化或半结构化的业务说明。我的思路是尽量保持一个业务规则片段的语义完整，不为了固定长度硬切。参考 RAG 常见经验，切分要同时考虑文档自然段落、检索粒度、模型上下文预算和重叠区域，避免把一个认证规则或设备约束切成无法独立理解的碎片。

## 14. 如果检索结果不准，你会从哪些方向优化？

参考答案：

我会先看问题出在召回还是生成。如果正确内容根本没进候选结果，就要优化知识切分、查询改写、关键词和向量混合召回、元数据过滤；如果候选里有正确内容但排序靠后，可以加规则重排或语义重排；如果检索结果是对的但回答不稳，就要加强提示词约束、引用要求和拒答策略。优化 RAG 不能只调模型，要看整条链路。

## 15. 你如何减少大模型幻觉？

参考答案：

我会从工程约束入手。第一，用 RAG 和业务数据库把回答锚定到外部可信信息，不让模型只靠参数记忆；第二，要求结构化输出，便于校验字段和枚举；第三，关键任务加规则兜底，模型失败时返回确定性结果；第四，高风险动作必须人工确认；第五，评估集里专门检查项目推荐是否幻觉、订单字段是否非法、写操作是否越权。

## 16. 为什么要求大模型输出结构化结果？

参考答案：

因为业务系统不能消费一段自由发挥的自然语言。订单草稿需要字段，项目推荐需要项目列表和理由，排程解释需要 SLA 风险、瓶颈和建议，异常分析需要风险等级和受影响订单。结构化输出让系统能够自动校验类型、枚举和必填项，也让评估服务能判断模型是否真的完成任务。

## 17. 如果大模型不可用，系统还能工作吗？

参考答案：

可以。这个项目把大模型设计成增强能力，而不是唯一依赖。没有模型服务配置、网络失败或模型输出异常时，系统会走规则兜底，比如用关键词和业务规则生成订单草稿、用确定性流程推荐必检项目、用排程指标生成解释和异常建议。这样即使模型暂时不可用，核心业务仍能继续运行。

## 18. 排程问题在业务上怎么抽象？

参考答案：

它接近动态柔性作业车间排程。订单可以看成任务，检测项目是工序，设备、人员、耗材、前处理工位和转运资源是约束资源，认证流程决定工序顺序，订单优先级和承诺完成时间决定 SLA 目标。现场还会有设备故障、人员缺勤、订单变更等扰动，所以排程必须支持动态重排和运行中步骤保护。

## 19. CP-SAT 在这个项目里解决什么问题？

参考答案：

CP-SAT 用来表达多约束排程问题，尤其适合设备互斥、工序先后、人员时间窗、耗材容量、班次窗口和运行中步骤锁定这类硬约束。相比纯规则排序，它能更系统地搜索可行解；但它也有规模和求解时间限制，所以项目里把它作为滚动窗口求解能力，并保留 SLA 兜底调度。

## 20. CP-SAT 的目标函数如何和业务目标对应？

参考答案：

业务目标不是单纯把所有订单排得最快，而是优先保障 SLA，尤其是 VIP 和加急订单。因此目标函数会把延期惩罚放在核心位置，并区分不同订单优先级。也就是说，VIP 延期的代价高于普通订单延期，同时还要考虑整体完工时间，避免为了局部订单牺牲整体交付效率。

## 21. 为什么还要设计 SLA 兜底策略？

参考答案：

因为优化求解器不是万能的。现场数据可能不完整，约束可能临时不可行，订单规模过大也可能导致求解超时。如果系统只有优化器，一旦求解失败就无法给业务输出结果。SLA 兜底策略的作用是保证任何时候都有一份可解释、可执行的排程，即使不是全局最优，也能按优先级和承诺时间尽量降低延期风险。

## 22. 运行中的检测步骤为什么要锁定？

参考答案：

真实检测现场不能因为系统重排就中断正在运行的设备或人员安排。比如一个样品已经进入环境仓或 EMC 测试，强行打断会造成数据无效或设备占用冲突。所以系统在重排时会保留运行中的步骤，把已开始的设备和人员时间段视为不可变，只调整未来还没开始的部分。

## 23. 事件驱动重排是怎么设计的？

参考答案：

现场扰动会以事件形式进入系统，比如订单变更、设备故障、人员不可用、耗材不足或检测完成。系统会对短时间重复事件做去重和防抖，避免频繁重排；高优先级事件可以尽快触发，普通事件可以批量处理。这样既能及时响应现场变化，又不会因为每个小变动都重算排程而造成系统抖动。

## 24. 设备、人员、耗材这些约束怎么统一处理？

参考答案：

我把它们都看成资源约束，但资源类型不同。设备强调互斥和容量，人员强调技能、角色、班次和并行上限，耗材强调每日容量，前处理和转运强调辅助资源占用。排程时每个检测步骤都必须同时满足这些资源条件；如果某类资源不足，订单不能硬排，而是进入阻塞状态并给出原因。

## 25. 异常分析 Agent 的价值是什么？

参考答案：

排程系统不只是输出一张表，还要解释为什么某些订单延期或阻塞。异常分析 Agent 会基于当前队列、设备状态、阻塞原因和 SLA 指标，生成结构化分析，比如主要瓶颈资源、受影响订单、风险等级和建议动作。它的价值是降低人工排查成本，但它只提供分析建议，不直接关闭事件或修改资源状态。

## 26. 通知生成为什么也要加安全边界？

参考答案：

通知会影响现场人员行动，所以不能让大模型随意改变触发条件。项目中通知触发规则由排程和业务服务决定，比如设备空闲、检测完成、SLA 风险、人员阻塞等；大模型只负责把通知标题和正文改得更清晰、更可执行，不改变通知类型、严重等级、触发时间和关联订单。这样既利用了模型的语言能力，又不让它控制业务状态。

## 27. 权限和审计在 AI 应用里为什么重要？

参考答案：

AI 应用一旦接入业务系统，就不能只关注回答质量，还要关注谁能做什么、系统做了什么。项目里不同角色有不同权限，查看排程、创建订单、重建排程、执行回写、查看通知都要区分。关键操作会记录审计日志，便于追踪责任。这样才能避免“模型建议”和“业务执行”混在一起。

## 28. 你怎么评估这个多 Agent 系统？

参考答案：

我会从三层评估：第一是回答质量，比如订单字段是否正确、项目推荐是否保留必检项、知识回答是否有依据；第二是执行轨迹，比如任务有没有交给正确的业务 Agent、是否出现不必要的跳转；第三是效率和安全，比如响应延迟、模型调用成本、格式解析成功率、兜底成功率，以及是否出现模型触发写操作的违规情况。评估不是让模型自评，而是用规则和测试集做门禁。

## 29. 如果面试官问 Loop Engineering 或反馈闭环，你怎么结合项目回答？

参考答案：

我会说这个项目还不是完全自主循环，而是“人在回路中”的工程闭环。触发器是订单变更、设备异常或人工请求；可验证目标是排程可用、SLA 风险降低、字段合法、无越权写操作；每轮结果会形成排程、通知、审计和评估记录；如果模型输出不合法或风险较高，就停止在人工确认环节。我的理解是现阶段 AI 应用不适合让模型无限自主循环，最稳妥的是让系统有反馈、有门禁、人能接管。

## 30. 这个项目的不足和后续优化方向是什么？

参考答案：

不足主要有三点：第一，真实 LIMS/ERP 厂商系统联调和真实历史调度数据还不足；第二，RAG 知识库和评估集规模还可以继续扩充；第三，CP-SAT 更适合滚动窗口，不适合无限大规模全量求解。后续我会优先接入真实业务样本，完善评估集和知识库，再考虑更强的检索策略、学习型排序或小规模微调，而不是让大模型直接替代排程算法。
