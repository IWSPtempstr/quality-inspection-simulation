# I2 导入失败与回滚 runbook

## 1. 回滚原则

- PostgreSQL 是权威源，回滚优先保证其一致性
- Chroma / BM25 是可重建层，必要时可整批丢弃并从 PostgreSQL 重建
- 不允许“部分导入成功 + 线上继续运行 + 以后再补”这种模糊状态

## 2. 回滚触发条件

满足任一条件即进入回滚：

- Goose migration 未完成或版本不一致
- 导入后关键表行数无法闭合
- 跨中心串写
- 发现未脱敏敏感字段
- 标准激活版本或检索层版本与 PostgreSQL 不一致且不能在窗口内修复
- 未评审 incident 进入长期检索索引

## 3. 回滚前冻结

1. 停止切换窗口内的新导入动作
2. 记录当前 `run_id`、故障时间、故障症状
3. 保留导入日志、拒绝记录、抽样证据
4. 由 `rollback_approver` 明确批准回滚

## 4. PostgreSQL 回滚

根据导入工具的批次边界，执行以下之一：

- 删除本次导入批次新写入的业务数据
- 或恢复到导入前数据库备份/快照

要求：

- 回滚后重新核对关键表计数
- 不得回退 Goose schema 版本，除非另有明确、已验证的回滚方案

## 5. Chroma / BM25 回滚

- 停用本次导入激活的 collection / index version
- 切回上一个仍在 rollback window 内的已验证版本
- 若当前版本不可用，直接清空本次构建产物并等待重建

Chroma 可按 I1 的备份/恢复脚本或版本切换记录回退；BM25 按同批次版本回退。

## 6. 回滚后验证

至少确认：

- PostgreSQL 关键表与导入前一致
- 活跃 Chroma / BM25 版本回到上一个已验证版本
- 新系统不暴露部分导入后的脏数据
- 证据模板中记录回滚原因、执行人、完成时间

## 7. 重新尝试条件

只有在以下条件满足后才允许再次导入：

- 根因已明确
- 输入文件或映射规则已修正
- 新的 manifest 已生成
- 业务 reviewer 和 rollback approver 重新批准
