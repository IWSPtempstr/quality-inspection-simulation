# I2 导入字段边界与脱敏要求

## 1. 权威边界

- PostgreSQL 是订单、资源、标准版本、异常案例评审状态的权威来源
- Chroma / BM25 只保存可重建的检索层数据
- Redis 不参与 I2 的持久导入
- RabbitMQ durable message、Inbox、Outbox、审批锁状态不得通过 I2 直接灌入

## 2. 允许导入的事实

### 2.1 订单与项目

允许导入：

- `orders`
  - 业务标识、中心标识、订单状态、优先级、承诺时间、到达时间、取消/完成时间等确定性字段
- `order_projects`
  - 订单与项目的对应关系、项目状态、复检来源关系

禁止导入：

- 历史“正式排程即真相”的直接覆盖数据
- 来自旧系统的自由文本推断字段
- 无法映射到 G4 状态机的中间态

### 2.2 资源

允许导入：

- 设备、员工、技能、班次、不可用窗口、有效期、软停用状态、单调 source version

禁止导入：

- 进程内锁状态
- 旧系统缓存/派生占用状态

### 2.3 标准与检索数据

允许导入：

- 标准文档版本主数据
- 解析后的 chunk 元数据
- 激活版本记录

禁止导入：

- 未声明来源哈希的 chunk
- 无法回溯到标准版本的 embedding 结果

说明：

- embedding、Chroma collection、BM25 index 必须可重建
- Chroma collection 激活通过版本记录切换，不通过手工改线上查询代码实现

### 2.4 历史 incident

允许导入：

- 脱敏后的事件事实：事件类型、中心、发生时间、影响对象、处理结果摘要

禁止导入：

- 自动标记为 `approved` 的长期异常案例
- 直接写入可被 A4/A6 检索的 reviewed case 索引
- 原始敏感正文、聊天记录、外部工单正文

## 3. 脱敏最低要求

以下信息在导入前必须移除或替换：

- 员工真实姓名、电话、邮箱、身份证件、个人地址
- 客户真实名称、联系人、电话、邮箱
- 原始伙伴系统 token、cookie、URL 中的敏感 query
- 可逆推到真实样品/客户的自由文本备注

允许保留：

- 稳定但脱敏后的业务键
- 中心内唯一、不可逆的员工/设备/订单映射 ID
- 排程和规则所需的结构化事实

## 4. 版本与一致性要求

- 所有时间字段使用带时区 ISO 8601 或数据库等价 UTC 表示
- 所有资源/项目事实必须带 `center_id`
- 所有标准/资源增量关系必须能解释 `source_version`
- 无法映射到新系统状态机或 schema 的旧字段只能进入备注，不得强行落库
